# Feature inventory: Cura and CuraEngine

Researched 2026-10-25 (VSS-4). Sources, all read, none run:

- Cura frontend `Cura@5bea2f8` (LGPL-3.0, `Cura/LICENSE`), github.com/Ultimaker/Cura
- CuraEngine `CuraEngine@47b0388` (AGPL-3.0, `CuraEngine/LICENSE`), github.com/Ultimaker/CuraEngine
- Uranium framework `Uranium@e65ccc1` (LGPL-3.0), github.com/Ultimaker/Uranium, cloned for this card
  because transform tools, STL/OBJ IO and the plugin registry live there
- Mesh Tools plugin README, https://github.com/fieldOfView/Cura-MeshTools (fetched 2026-10-25)

Method: `fdmprinter.def.json` and `fdmextruder.def.json` were parsed with `python3 -I` (json module,
walking `settings` -> `children`). Raw dump with full one-line descriptions and the enum option
lists: `.reference/notes/VSS-4-features-cura.md`. In section 1, `Lnnn` is the line where the setting
object opens in `Cura@5bea2f8:resources/definitions/fdmprinter.def.json` (or `fdmextruder.def.json`
in 1b). Flags: `M` = `settable_per_mesh`, `E` = `settable_per_extruder`.

## Findings

### 1. Settings from fdmprinter.def.json and fdmextruder.def.json

`fdmprinter` has 740 settings in 17 categories: machine_settings 70, resolution 15, shell 34,
top_bottom 50, infill 36, material 60, speed 76, travel 25, cooling 17, support 110,
platform_adhesion 79, dual 30, meshfix 16, blackmagic 15, experimental 95, ppr 7,
command_line_settings 5. Types: float 494, bool 122, int 49, enum 34, str 11, optional_extruder 9,
`[int]` 9, extruder 9, polygons 2, polygon 1. `fdmextruder` adds 31 per-extruder settings (float 18,
str 9, bool 2, int 1, extruder 1).

How a setting is defined (property counts over 757 nodes, 740 settings plus 17 categories):
`default_value` 739, Python-expression `value` 357, `enabled` 552, `minimum_value`/`maximum_value`
452/195, warning bounds 236/358, `limit_to_extruder` 340, `resolve` 46 (how a global value is
derived from per-extruder values), `settable_per_mesh` 713, `settable_per_extruder` 460,
`settable_per_meshgroup` 104, `settable_globally` 14. The formulas are evaluated in the frontend,
not the engine (section 4). The values of a setting come from a stack of containers: user,
quality_changes, intent, quality, material, variant, definition_changes, definition
(`Cura@5bea2f8:cura/Settings/CuraContainerStack.py:409-419`). The repo ships 707 machine definitions
plus `extruders/`, `quality/`, `intent/` and `variants/` (`Cura@5bea2f8:resources/`).

Enum options worth knowing (full list in notes): `infill_pattern` lines, trihexagon, cubicsubdiv,
tetrahedral, quarter_cubic, concentric, zigzag, cross, cross_3d, gyroid, lightning, honeycomb,
octagon, grid, cubic, triangles; `support_structure` normal, tree; `adhesion_type` skirt, brim, raft,
none; `z_seam_type` back, shortest, random, sharpest_corner; `retraction_combing` off, all,
no_outer_surfaces, noskin, infill; `prime_tower_mode` normal, interleaved; `print_sequence`
all_at_once, one_at_a_time; `magic_mesh_surface_mode` normal, surface, both; `machine_gcode_flavor`
RepRap (Marlin/Sprinter), RepRap (Volumetric), RepRap (RepRap), UltiGCode, Griffin, Cheetah,
Makerbot, BFB, MACH3, Repetier, BambuLab.

### 4. Frontend/engine protocol and multi-extruder handling

Transport: the frontend (`CuraEngineBackend`) listens; it launches
`CuraEngine connect 127.0.0.1:<port>` (`Cura@5bea2f8:plugins/CuraEngineBackend/CuraEngineBackend.py:303-315`).
Messages are protobuf over libArcus, schema `CuraEngine@47b0388:Cura.proto` (a copy lives in
`plugins/CuraEngineBackend/Cura.proto`). The engine registers message types at
`src/communication/ArcusCommunication.cpp:293-306`.

Frontend to engine, one `Slice` message (`Cura.proto:34-45`):

- `object_lists`: mesh groups, one per object in one-at-a-time mode (modifier meshes copied into
  each), otherwise one (`StartSliceJob.py:167-200`). Each `Object` carries raw float32
  vertices/normals, int indices, a name, per-object setting overrides, and optional UVs and a PNG
  texture for painted data (`Cura.proto:53-63`).
- `global_settings`: every global setting, already evaluated, as name and UTF-8 string value
  (`StartSliceJob.py:498-535`). The frontend evaluates all `value` formulas; it also pre-computes
  `material_*_temp_prepend` by regexing the start G-code (`:513-525`).
- `extruders`: per extruder, only settings flagged `settable_per_extruder` (`:470-495`).
- `limit_to_extruder`: setting name to extruder index, so e.g. support settings come from the
  support extruder (`:541-553`).
- per-object overrides resolved with their limit-to-extruder stack (`:556-600`).
- `engine_plugins`, version, Sentry/user metadata.

The engine has no defaults on this path. `Settings::get` checks the object's own settings first,
then `limit_to_extruder`, then the parent chain (mesh, mesh group, extruder, global); on a missing
key it logs an error and calls `std::exit(2)`, so the engine process terminates
(`CuraEngine@47b0388:src/settings/Settings.cpp:66-86`; parsing
`src/communication/ArcusCommunicationPrivate.cpp:55-162`). The typed getters (enums, polygons,
`FlowTempGraph`, etc.) are at `Settings.cpp:90-657`.

Engine to frontend (handlers at `CuraEngineBackend.py:153-160`):

| Message | Content |
|---|---|
| `Progress` | 0..1 |
| `LayerOptimized` (and legacy `Layer`) | per layer id, z, thickness, path segments: extruder, points, `line_type` per segment (15 feature types incl. inset0/x, skin, support, infill, travel, prime tower), width, thickness, feedrate, attributes such as overhang/bridge (`Cura.proto:70-125`) |
| `GCodeLayer` | G-code text in chunks |
| `PrintTimeMaterialEstimates` | time per feature type and per-extruder length/weight/cost (`Cura.proto:134-159`) |
| `InitialExtruder`, `SliceUUID`, `SlicingFinished` | bookkeeping |

The frontend turns layer messages into `LayerPolygon` meshes for SimulationView
(`plugins/CuraEngineBackend/ProcessSlicedLayersJob.py:100-178`). The engine also has a CLI mode
(`CuraEngine connect|slice|help`, `src/Application.cpp:244-260`; `slice` takes `-j` definition JSON and `-s key=value` among other flags, `src/communication/CommandLine.cpp:193-337`) and an
Emscripten build (`src/communication/EmscriptenCommunication.cpp`).

Multi-extruder: each extruder is a separate stack (`fdmextruder.def.json` plus extruder definition,
variant, material); objects choose an `extruder_nr` (per-mesh); features choose an extruder via
`optional_extruder`/`extruder` settings (e.g. support, adhesion, skirt/brim, infill/wall extruder);
global values derived from extruders via `resolve`. Machine options: extruder count (L270), shared
heater (L410), shared nozzle (L420), extruder offsets, `machine_use_extruder_offset_to_offset_coords`
(L523). Engine handles prime tower (normal or interleaved, L8035/L8046), ooze shield (L8223),
standby temperatures and pre-heat (`src/Preheat.cpp`), extruder switch cooling
(`cool_during_extruder_switch`), `multiple_mesh_overlap`/`carve_multiple_volumes` (L8494/L8506),
interlocking structure between materials, and painted multi-material via `MeshMaterialSplitter`.

## Implications for VSSlicer

- Reuse the shape of Cura's settings schema: JSON definitions with categories, types, units,
  bounds, `enabled`, per-mesh/per-extruder flags, `limit_to_extruder`. It suits a VS Code settings
  UI and JSON Schema well. We can read `fdmprinter.def.json` as data (LGPL frontend resource).
- Running CuraEngine as an external process is attractive for a VS Code extension: one `Slice`
  protobuf in, layer paths and G-code out, no GUI coupling. But we must then evaluate the formulas
  ourselves (a Python-expression subset) because the engine expects every key. Spawning the AGPL
  engine as a separate unmodified binary is arm's-length use; linking or modifying it is not.
- `LayerOptimized` gives typed segments (feature, width, height, feedrate); that is exactly what a
  G-code preview with toolhead simulation needs, without parsing G-code.
- Painted data via UV texture, gRPC slots and post-processing chunks are hooks we could use with
  an unmodified engine.
- Skip Ultimaker cloud, Digital Library, UM3 network, Sentry.
