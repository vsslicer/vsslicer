# Spike PRF-43: is the flattened Prusa export byte-equivalent?

Date 2026-10-26. Worker sp10-prf-43, reviewed by sp10-rev-prf-43 (probes re-run, cited lines checked).

Sources (read only, AGPL-3.0): PrusaSlicer-2.9 at `b028299c770b8380ee81c921a2867d522f288123`
(`src/libslic3r`, `resources/profiles/PrusaResearch.ini`), referred to below as `PS@b028299c`;
oracle output files from PrusaSlicer at `30ef59195e0f3ee6f270b185bb5f9fb5f349f81f` (`PS@30ef5919`).
Probes and raw output: `.reference/notes/PRF-43-probe/` (`probe.mjs`, `probe-user.mjs`, `out3.txt`), raw notes
`.reference/notes/PRF-43-flatten-export.md` (both ignored, kept locally).

## Answer

- **Vendor presets: no, and they cannot be.** The flattened form has lost `inherits` and the section's key
  order, so the vendor section text cannot be rebuilt from it, and PrusaSlicer itself never writes it back.
- **Files PrusaSlicer writes (user presets): yes.** Header kept verbatim, keys byte-sorted, stored values
  verbatim, `key = value\n` reproduces a real PrusaSlicer file byte for byte.

## Model check

The serializer model in `probe.mjs` (`g()`, `canon()`) is a fixed point on every typed line of four real
PrusaSlicer outputs (`PS@30ef5919:tests/data/default_fff.ini` 307/307; the config blocks of
`test_sequential`, `test_vase`, `test_multimaterial` `.gcode` 353/353 each). All four are byte-sorted.
An empty value is written `key = ` (trailing space).

Review mutation probes: dropping the `%` on percent types drops the oracle to 300/307 and 345/353;
dropping `coStrings` escaping drops it to 306/307 and 352/353. The `%g` exponent and 6-digit rounding
paths are covered only by the probe's own asserts: no oracle or bundle value exercises them.

None is byte-equal. Causes, largest first:

1. **Defaults.** PrusaSlicer writes every option of the preset type (print 198, filament 86, printer 90 keys);

   bytes are unverified until a PrusaSlicer 2.9 run.
2. **Dropped keys.** Printer `octoprint_apikey`, `octoprint_host`, `serial_port`, `serial_speed`; the

3. **Re-serialized values** (whole-bundle numbers below).
4. **Against the vendor section text:** `inherits` lines gone; source key order lost (9 of 10 sections are not

## Real user file round trip

`default_fff.ini` imported as a `print/`, `filament/` and `printer/` user preset: 311 keys, 0 diagnostics each.
Header lines verbatim + keys sorted + values verbatim + `key = value\n` reproduces the file byte for byte for all
three kinds. `PrusaNative` has no field for the header line or the line ending today; a byte-equal writer needs one.

## Decisions for the writer (PRF-52)

- **Target:** byte equivalence is defined against the stored native form, not the vendor section text. For vendor
  presets: `export(import(x))` is stable and `import(export(import(x))).values` deep-equals `import(x).values`.
  User files PrusaSlicer wrote round-trip byte for byte.
- **Key order:** byte-sorted, always, as `std::map` does (UTF-16 sort is equal for the ASCII key set).
- **Lines:** `key = value` with single spaces, empty as `key = `; header `# generated by ...` kept from the
  source when present, else written fresh; LF line endings (CRLF on Windows from text-mode `ofstream`: unverified).
- **Numbers:** untouched keys keep their stored text (`0.20` stays `0.20`; PrusaSlicer reads both). Edited keys
  use PrusaSlicer's serializer: `%g` precision 6, `,` joins without space, `%` on percent types, `nil` for
  nullable, `0`/`1` bools, the two string escapers above.
- **Keys:** the native writer adds no defaults (missing keys take type defaults on load, `PresetBundle.cpp:1612-1622`).
  Keys outside the type's option list (`*_settings_id`, `renamed_from`, `octoprint_*`) are harmless on load but are
  left out when writing from unified data; a verbatim round trip keeps them.

## Licence

The serializer rules above are behaviour read from AGPL-3.0 source. `probe.mjs` reimplements that behaviour
(`%g` via JS number formatting, the escape rules as regexes); it copies no PrusaSlicer code. PRF-52 should port
from the probe and this description, not translate the C++ functions line by line.
