The foundation of `@vsslicer/profiles`: the entity model (vendor, printer_model, nozzle, surface, feeder, material, process, printer_instance) published as JSON Schema, a settings catalogue that places every native setting key of PrusaSlicer, SuperSlicer, Bambu Studio, OrcaSlicer and Cura into one set of schema groups, and a safe condition evaluator in TypeScript. Every other PRF epic, the slicer adapters (SLC) and the filament inventory (FIL) read profiles through these types; users see the result as completion and diagnostics when they edit a profile file, and as the group structure of the generated form (E15).

## Scope
- In: entity types and JSON Schema per `profiles.md` §6 (shared fields `id`, `inherits[]`, `abstract`, `when`, `overrides[]` with `match: first|all`, `settings`, `renamed_from[]`, `meta`); keyed per-extruder values (`{"0": .., "1": ..}`) and `null` for fall-through; the merge rules (left-to-right parents, child last, maps deep-merged, arrays replaced); cycle and unknown-parent detection as errors; the expression language (literals, `== != < <= > >=`, `=~ /re/`, `!~`, `in [..]`, `and/or/not`, parentheses, namespaces `printer.* nozzle.* surface.* feeder.* material.* process.*`); a per-vendor keyword-to-tag table for Prusa `printer_notes` tests.
- In: the settings catalogue, one entry per unified key: group, home entity, type, unit, enum, bounds, default, per-extruder flag, label, tooltip, native names per dialect and a conversion (scale, sign flip, percent-of, enum map). Generated by a script from `OrcaSlicer@09aa0114:src/libslic3r/PrintConfig.cpp`, `PrusaSlicer@b028299` and `@30ef591` definitions, SuperSlicer `.ui` groups and `Cura@5bea2f8:resources/definitions/fdmprinter.def.json` and `fdmextruder.def.json`. Labels and tooltips may be ported (AGPL and LGPL text, D2) with a provenance line per entry.
- In: multi-tool shape: `printer_instance.toolheads[{slot, nozzle}]`, `feeder {type: mmu|ams|toolchanger, slots}`, per-extruder keys; enough to import Prusa 3.0 `printer_config` (XL 2T), Orca IDEX and Bambu H2D/H2C extruder-variant arrays.
- Out: reading native files (E12), files on disk and resolution over a store (E13), any UI (E14, E15), SLA and milling groups (E58), Cura `=expr` evaluation (stored verbatim; see Risks).

Group sums above are the matrix cells added up (the matrix lists the printer Extruder pages under both extrusion and printer definition; here they count once, under `machine`); keys on no GUI page land in the group of their nearest category and are flagged `hidden`.

## Feature-matrix rows
- The fourteen §1 rows above (P0 except Multi-material, Special modes and Plate-level, which are P1): done when every native key of that category is in the catalogue under its group, typed, with its native names and conversion, or marked native-only with its dialect. P1 groups are schema and pass-through only; no dedicated UI beyond the generated form.
- §13 Inheritance and compatibility conditions (P0): done when merge rules and the evaluator pass the truth table and every Prusa, Orca, Bambu and Cura compatibility construct in the `profiles.md` §6 conversion table has a unified form.
- §13 Nozzle or tool as its own entity (P0): done when `nozzle` and `surface` are entities and per-nozzle printer presets can be expressed as `printer_model` + `nozzle` + `overrides`.
- §14 Filament presets (P0): done when `material` carries type, diameter, density, cost, temperatures, flow and `external_ids` (Cura GUID, Bambu and Orca filament IDs, Prusa name).
- §5 Multi-tool presets and toolchangers (P2, schema side): done when XL 2T, IDEX and H2C dual-extruder fixtures validate and keep per-extruder values without positional arrays.

## Acceptance criteria
- [ ] JSON Schema (draft 2020-12) for each entity; every hand-written fixture validates and every negative fixture fails with the expected path.
- [ ] Catalogue coverage test: every key in the pinned key lists (Orca@09aa0114, Bambu@79df7ae, Prusa@b028299 and @30ef591, SuperSlicer@1f3d287, Cura@5bea2f8) is mapped or native-only; zero unassigned keys; group counts match the table within the documented `hidden` keys. Catches a new upstream key silently dropped.
- [ ] The 56 mapped keys of `profiles.md` §6 convert both ways with their notes (90-x support angle, Cura flow x100, elephant-foot sign flip, per-plate bed temperatures) as unit tests.
- [ ] Evaluator truth table: at least 50 conditions sampled from the 822 in `PrusaResearch.ini` and the 3.0 YAML forms, against printer fixtures, matching PrusaSlicer's results as computed by hand from `Preset.cpp:390-421`; parse failures return `compatible` plus a diagnostic, as PrusaSlicer does.
- [ ] Merge tests: last parent wins, deep-merged maps, `null` fall-through, cycle and unknown parent raise typed errors.
- [ ] Evaluator has no `eval`, `Function` or dynamic import; a fuzz test of 10 000 random inputs never throws outside its error type.
- [ ] Verified on fixtures only; no hardware involved (D5).

## Risks and spikes
- Canonical key names (`profiles.md` open question). Proposal: Orca names are canonical, since the first engine is the Orca CLI (I5) and Orca covers Bambu except about 100 keys; other dialects map through the catalogue. Spike (1 day) writes it up as a VSS decision before the catalogue script runs.
- Cura `=expr` values: kept as `{"expr": "..."}`; evaluation belongs with E28's settings resolution. Coordinator question: one shared evaluator, owned where.
- Prusa 3.0 YAML is alpha (`@30ef591`); its hardware namespaces may change. Mapping is pinned and its tests are tagged so a schema change shows as a failing pinned test, not drift.
- Group mapping is a judgement (matrix: "the mapping is ours"); spike: review the catalogue's group of each hidden key with the VSS-3 dump.

## Eng review
- Scope: largest PRF epic (about 5 sprints). The catalogue could split into its own epic; kept here because importers need entities and catalogue together and both ship as one library. Split point if it overruns: catalogue generation script and coverage test become a follow-up epic, E12 starts with the 56 mapped keys.
- Tests name the regression they catch (upstream key drift, wrong condition result, merge order). Oracles: pinned upstream sources and PrusaSlicer's own rules.
- Boring technology: TypeScript, JSON Schema, a hand-written recursive-descent parser; no innovation token.
- Blast radius: a wrong merge rule corrupts every resolved profile and every slice; hence the merge and truth-table suites gate release.
- Zero silent failures: unmapped key, unparsable condition, cycle, unknown parent each have a typed error and a diagnostic consumed by E14.

## Coordinator reconciliation

- Canonical setting keys are Orca's names (D9). The Cura `=expr` evaluator is SLC's (the CuraEngine adapter epic); PRF stores formulas as written. Record for each setting where it may be overridden (object, part, height range) for the VWR object-editing epic.
